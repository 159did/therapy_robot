# PTR 理疗机器人仓库使用说明

这是一份面向课题组成员的实验软件仓库说明。项目的 GitHub 地址是：

`git@github.com:159did/therapy_robot.git`

当前仓库是 **Private（私有）**。只有被仓库管理员邀请的 GitHub 账户才能看到和下载代码。

## 一、这个库由什么组成

可以把仓库理解成“机器人软件、实验数据、测试和操作记录放在一起的工程档案”，主要部分如下：

| 目录或文件 | 作用 |
| --- | --- |
| `src/`、`include/` | C++ 核心程序，包括运动学、碰撞边界、流程和接口实现（以仓库实际目录为准） |
| `scripts/` | Python 和 Shell 工具，例如离线视觉处理、标定数据处理、仿真运行和检查脚本 |
| `web/` | 网页控制界面和前端绑定 |
| `tests/` | Python、C++ 和接口测试；这些测试默认是离线的 |
| `config/` | 运行配置、机箱碰撞边界和示例配置；其中部分配置与实体设备有关 |
| `calibration/` | 轴、相机、机械零点等标定记录；其中可能包含真实实验数据 |
| `back/`、`data/` | 背部图像、D405 样本和视觉处理中间结果；只用于课题实验和离线分析 |
| `docs/`、`progress/` | 接口契约、阶段说明、实验记录、验证证据和路线图 |
| `.github/workflows/` | GitHub Actions 自动验证流程；推送或 Pull Request 后自动运行软件测试 |
| `CMakeLists.txt` | C++ 工程构建入口 |
| `README.md`、`CONTRIBUTING.md`、`SECURITY.md` | 项目入口、协作规则和敏感信息规则 |

目录名称会随着开发继续增加或调整；实际以当前 `main` 分支为准。

## 二、别人下载后可以做什么

在获得私有仓库访问权后，成员可以：

1. 下载代码、文档、测试和已经归档的实验资料。
2. 在自己的电脑上编译 C++ 程序，运行离线仿真和软件测试。
3. 阅读和修改视觉、运动规划、网页界面、接口契约及文档。
4. 用合成数据或已批准的实验样本复现问题、补充测试和比较算法。
5. 建立自己的分支，提交改动并发起 Pull Request，让其他成员审核。

下载仓库本身不会自动连接 Nano，也不会自动打开串口、访问 D405 或让电机运动。默认工作流只做软件构建和离线验证。

## 三、下载方法

推荐使用 SSH。成员先把自己的 GitHub 账户加入仓库，并在本机配置好 GitHub SSH 公钥，然后执行：

```bash
git clone git@github.com:159did/therapy_robot.git
cd therapy_robot
```

检查当前分支和远端：

```bash
git status
git remote -v
```

第一次下载后，可以先运行软件验证：

```bash
python3 scripts/github_private_preflight.py --root .
python3 -m unittest discover -s tests -p 'test_*.py'
cmake -S . -B build/local -DBUILD_TESTING=ON
cmake --build build/local --parallel 2
ctest --test-dir build/local --output-on-failure
```

如果本机没有 C++ 编译环境，可以先只运行 Python 测试，并把环境缺失写在 Pull Request 中。

## 四、别人怎样把代码上传到你的库

“能下载”不等于“能直接改 `main`”。推荐流程是：

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/my-task
```

完成修改后，在本地运行相关测试，再提交：

```bash
git add <修改过的文件>
git diff --cached --check
git commit -m "describe the change"
git push -u origin feature/my-task
```

然后在 GitHub 上创建 Pull Request，目标分支选择 `main`。Pull Request 至少要说明：

- 改了什么，以及没有改什么；
- 执行过哪些测试，结果是什么；
- 是否涉及真实设备、串口、D405 或电机；
- 仍然存在的限制或待办事项。

GitHub Actions 会自动运行软件验证。审核通过且检查为绿色后，由仓库管理员合并。不要使用以下命令把所有本地分支或标签一次性上传：

```bash
git push --all
git push --mirror
git push --tags
```

如果只是个人实验分支，也可以只推送该分支，不会影响 `main`：

```bash
git push -u origin feature/my-task
```

## 五、权限和实体硬件边界

GitHub 权限只管理代码仓库，不等于 Nano 或机械臂的控制权限。当前默认边界是：

- 软件任务可以访问代码、离线测试和仿真；
- 未经负责人明确批准，不访问实体串口、D405 或 Nano；
- 不使能、回零、置零、jog 或移动实体电机；
- 实体测试必须单独安排时间、人员和安全检查；
- 把代码合并到 `main` 不代表已经获得实体运行授权。

涉及真实设备的任务，必须在任务说明和 Pull Request 中单独标明，不能因为 CI 通过就直接接入硬件。

## 六、哪些文件不能随便外传

本仓库是私有库，因为其中包含真实实验相关内容。尤其注意：

- `config/jetson-hardware.env` 等实体设备配置；
- `calibration/` 中的真实轴 offset、K0 和相机标定记录；
- `back/`、`data/` 中的背部图像、D405 样本和实验中间结果；
- 文档、日志和证据中的本机路径、设备地址或运行细节。

不要把 SSH 私钥、GitHub Token、密码、真实设备凭据或未经脱敏的个人图像提交到 Git。发现疑似敏感信息时，先停止推送并通知管理员；仅删除当前文件并不能清除 Git 历史。

更具体的规则见 [`CONTRIBUTING.md`](../CONTRIBUTING.md)、[`SECURITY.md`](../SECURITY.md) 和 [`PUBLISHING.md`](../PUBLISHING.md)。

## 七、最简单的协作例子

例如 2 号同学要改离线视觉算法：

```bash
git clone git@github.com:159did/therapy_robot.git
cd therapy_robot
git switch -c feature/offline-vision
# 修改 scripts/ 和 tests/，只使用离线图片
python3 -m unittest tests/test_offline_vision_pipeline.py
git add scripts tests
git commit -m "improve offline vision pipeline"
git push -u origin feature/offline-vision
```

2 号在 GitHub 发 Pull Request；负责人检查差异和测试结果，GitHub Actions 通过后再合并。整个过程不需要连接 Nano，也不需要让机械臂动作。

## 八、遇到问题先看哪里

- 不知道项目现在做到哪一步：看 `README.md` 和 `docs/progress/`。
- 不知道能不能运行实体设备：先看任务说明和 `SECURITY.md`，不要自行尝试。
- 不知道测试怎么跑：看 `docs/software-validation.md`。
- 不知道怎么发 Pull Request：看 `CONTRIBUTING.md`。
- 不确定文件能不能上传：先运行 `python3 scripts/repository_safety_scan.py --root .`，再询问管理员。
