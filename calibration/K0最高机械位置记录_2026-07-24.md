## 为什么不把 129 native 直接当成最高点绝对编码器值

当前模式是 `hardware_relative`。程序启动时把当时读取的物理多圈位置保存为本次运行的临时偏置，然后 API 返回：

```text
逻辑位置 = 方向 ×（物理多圈位置 - 本次启动偏置）
```

因此 API 中的 `129 native` 是相对本次启动位置的逻辑反馈，不是 MG6012E-i8B 的绝对多圈原始读数。当前 API 又没有公开启动偏置，所以不能从这一个值可靠地反推出绝对物理多圈位置。

本记录故意区分：

```text

逻辑快照：已记录
绝对多圈原始最高点：已单独读取为 -933 native
K0 零位写入：未执行
五轴软件零位捕获：未执行
```

## 最高位置绝对多圈原始记录

在 K0 已下电、抱闸已合且主控制进程释放串口后，使用 MF/MG 协议只读命令 `0x92` 连续读取 5 次：

```text
-933
-933
-933
-933
-933
```

因此保存：

```text
K0_UPPER_RANGE_MAX_RAW = -933 native
```

读取过程没有发送上电、松闸、位置、速度、力矩或置零命令。5 次位置结果完全一致；抱闸状态 4 次确认已合，1 次状态读取超时，之后再次确认已合。

最终最大行程要在收纳位置读取 `Pzero` 后计算：

```text
K0_max_native = Pzero - (-933)
K0_max_mm = K0_max_native / 14400

正式坐标：
收纳位置 = 0 mm
最高位置 = +K0_max_mm
```

## K0 换算依据

```text
电机：MG6012E-i8B
协议：36000 native = 电机转子 1 圈
内部减速比：1:8
同步轮：72:72
滚珠丝杠导程：20 mm/输出轴转

1 native 对应位移
= 20 / (36000 × 8) mm
= 1 / 14400 mm
= 0.000069444444 mm
```

## 方向结论

记录时配置为：

```text
THERAPY_ROBOT_AXIS_DIRECTIONS=1,1,1,1,1
```

当时 K0 收到负方向目标，现场观察到机械臂上升并到达最高位置，因此当前方向配置下：

```text
K0 逻辑负方向 = 实体上升
```

项目现在明确约定“收纳位置为 K0=0，向上运动为正值，最高位置为移动范围最大值”。因此后续应把 K0 方向改为 `-1`：

```text
THERAPY_ROBOT_AXIS_DIRECTIONS=-1,1,1,1,1
```

修改方向后，可在当前最高位置重新建立本次运行的临时参考，再以 5 mm 低速点动验证“负方向是否下降”。等机械臂到达收纳位置后读取 `Pzero`，最终把收纳定义为 0、最高定义为正最大值。

## 急停原因

修正机械换算后，默认软限位余量仍为全轴共用的 `100 native`。对 K0 来说：

```text
100 / 14400 = 0.006944 mm
129 / 14400 = 0.008958 mm
```

最高点附近仅约 0.009 mm 的逻辑正向偏差就超过了约 0.0069 mm 的余量，从而触发：

```text
soft-limit violation K0
```

因此还需要把软限位余量改为按轴配置，不能用同一个 native 数值同时约束不同减速比和单位的五个轴。

## 后续正确步骤

1. 保持 K0 下电且抱闸合上，保留当前最高机械位置；
2. 增加按轴软限位余量；
3. 将 K0 软件方向改为 `-1`；
4. 重启时只建立临时相对零位，不执行电机 RAM/ROM 硬件置零；
5. 单独读取或保存 K0 最高点物理多圈原始位置；
6. 用 `-5 mm` 验证实体是否下降约 5 mm；
7. 用 `+5 mm` 返回最高点，确认不会持续顶住机械限位；
8. 其他四轴到达收纳姿态后，才执行完整五轴软件收纳零位捕获。
